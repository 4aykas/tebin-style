# tebin-style

A registry of brand themes for AI agents: DTCG tokens, brand assets, design
rules, an MCP server and a skill. TypeScript ESM, strict, tests in
`test/*.test.ts` (vitest).

## Commands

Node 22 and pnpm 11 (pinned in `packageManager`). Run `pnpm install` first.

- `pnpm verify`: the gate. Typecheck, validate, lint themes, check drift, test.
  CI runs it on Linux (Gitea) and Windows (GitHub). It must pass before you
  commit.
- `pnpm build`: regenerate every generated file, including the MCP bundle.
- `pnpm build:mcp`: rebuild only `mcp/dist/server.mjs`.
- `pnpm start:mcp`: run the bundled MCP server over stdio.

Dependency updates are manual: `pnpm update`, then `pnpm build`, then
`pnpm verify`.

## Layout

- `themes/<id>/`: one theme. Sources are `tokens.json`, `theme.json`,
  `design.intro.md` and `assets/` (except `assets/png/`). Brand themes add
  `sources.json`: each token's value and where it came from, checked by
  `pnpm lint:themes`. Adding a theme: follow the checklist in
  `CONTRIBUTING.md`.
- `rules/rules.json`: design rules.
- `src/`: the library. `scripts/`: build, check and release scripts.
- `mcp/`: the MCP server, bundled to `mcp/dist/server.mjs`.
- `skills/tebin-style/`: the agent skill. `.claude-plugin/`: the plugin and
  marketplace manifests.
- `docs/plans/`, `docs/specs/`, `docs/audits/`: dated history. Current
  values live in `themes/*/tokens.json`, `theme.json` and `rules/rules.json`.

## Generated files

These are generated by `pnpm build` and committed. Never edit them by hand:

- `themes/*/dist/**`, `themes/*/DESIGN.md`
- `themes/*/assets/png/**`, `themes/*/preview/**`
- `registry/index.json`, `rules/dist/**`
- `mcp/dist/server.mjs`, `llms-full.txt`

Change the source, run `pnpm build`, commit both. `pnpm check` fails CI when
a generated file is stale.

## Repository

The home is Gitea, `git.tebin.co/tebin-oss/tebin-style` (`origin`): pull
requests, issues, CI and releases. GitHub `4aykas/tebin-style` (`github`)
is a public push mirror. Raw URLs, the plugin marketplace and the GitHub
release read from it, so its `main` matches Gitea's. Push to `origin` only;
`.claude/hooks/mirror-guard.mjs` denies `gh pr`, `gh issue`,
`git push github` and `--no-verify`. `main` takes changes only through a Gitea PR with green
CI: push a branch, then `node scripts/gitea-api.mjs pr "<title>" [body-file]`,
`watch <sha>` and `merge <n>`; `logs <run>` cuts a red run to its failures,
`get <path>` reads any other endpoint. A PR that changes `src/`, `scripts/` or
`mcp/` gets `/code-review` on its branch before `merge`.
`.githooks/pre-push` runs `pnpm verify`.

## Release

- Review the diff since the last tag against `CODING_STANDARDS.md`
  (`/code-review`, base: the last `v*` tag), then run
  `node scripts/release.mjs <version> --reviewed` from `main`. It does every
  step below through a PR and stops at the first red one; add `--resume` to
  go on from there. It and `gitea-api watch` wait on CI for minutes: run
  them in the background, unpiped, and read the exit code.
- Push a tag `v<version>` from a commit on `main`. The tag must equal the
  `package.json` version, and `CHANGELOG.md` needs a `## <version> — <date>`
  entry (`scripts/check-release.mjs`).
- The package is private. There is no npm publish. Both releases attach the
  brand ZIP, the skill ZIP and a SHA-256 file per ZIP: Gitea's from
  `.gitea/workflows/release.yml`, GitHub's, which adds build provenance, from
  the mirrored tag.

## Boundaries

- `.input/` holds private brand material. It stays untracked.
- Changing a brand value (colour, type, logo) needs the owner's decision.
  See #72, #73, #74.

## Agent skills

### Issue tracker

Issues live on Gitea (`tebin-oss/tebin-style`), driven via its REST API. See `docs/agents/issue-tracker.md`.

### Triage labels

The five canonical triage roles use their default label strings (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`). See `docs/agents/triage-labels.md`.

### Domain docs

Single-context: one `CONTEXT.md` and `docs/adr/` at the repo root (created lazily by `/domain-modeling`). See `docs/agents/domain.md`.
